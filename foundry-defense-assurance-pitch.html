Foundry Defense Assurance

Test the attack. Prove the infrastructure holds.

Full kill-chain simulation for Foundry agents, with correlated evidence that the surrounding governance controls stop unauthorized impact - even when the agent attempts an unsafe action.

The problem: a refusal is not proof of protection

An unsuccessful attack can mean the model refused, an infrastructure control blocked it, or the evidence is missing. Our proposed platform distinguishes these outcomes, helping security leaders, platform admins, and agent developers establish which protections actually cover their deployment.

The promise: demonstrate independent enforcement across five defense dimensions, reconstruct the attack chain, and deliver an actionable evidence pack. This is infrastructure assurance powered by attack simulation, not another model-quality benchmark.

Five defense dimensions

DimensionWhat the customer needs to demonstrate
Network isolationAgent and dependency paths respect approved network boundaries; unintended public and cross-environment paths are rejected.
Gateway protectionRelevant traffic traverses APIM; configured request and token limits hold, and alternate routes do not bypass them.
Safety guardrailsRequired content-safety policies are attached to tested paths and explicitly block prohibited content scenarios.
Ingress / egressOnly approved callers reach the agent, and agent-initiated connections reach only approved destinations.
Access controlPrivileged operations require the correct identity, scoped permissions, and any required human approval.

One campaign, multiple enforcement points

In a sandbox support-agent deployment, adversarial test content attempts to redirect the agent toward a prohibited tool operation and a controlled external destination. Companion scenarios exercise unauthorized ingress, configured content blocks, and deliberately small gateway quotas. Each scenario declares its expected stop point, tested identity, route, configuration version, and observation window.

End-to-end chain

Untrusted entry > attempted redirection > tool invocation > permission or network boundary > simulated impact. Keep defenses intact. A blocked early stage is a valid result; later stages are not exercised, not automatically passed.

Targeted boundary exercises

Use separately labeled, authorized probes to reach downstream controls when the model refuses or an earlier layer blocks. A controlled tool replay uses the representative identity and route; it proves boundary behavior, not an end-to-end agent compromise.

Signal capture is the product's evidence foundation

Preflight diagnostics, trace coverage, permissions, and data arrival delays. Collect source event IDs, request/trace identifiers, execution identity, configuration snapshots, and controlled backend outcomes. Bind them to a simulator-issued run ID where supported; timestamp proximity alone does not prove causality.

Foundry tracing supplies execution visibility [3]. Azure Activity Log records control-plane changes, not every agent action; supported data-plane resource logs require separate diagnostics [6]. Sentinel supplies configured detection and incident evidence, not inline prevention [5]. Missing or sampled telemetry creates an explicit evidence gap.

Illustrative finding: authorization held; detection needs attention.

The agent attempted an unauthorized refund. The tool API denied the agent identity and the synthetic ledger remained unchanged. Access control passed for this scenario. No expected Sentinel alert appeared after the agreed window; investigate detection only after confirming telemetry completeness. A model refusal alone would not establish this result.

Focused first pilot

One Foundry sandbox deployment, applicable APIM routes, scoped tool identity, controlled backend and destination, and configured telemetry/Sentinel integration. Cover all five dimensions with paired permitted/prohibited scenarios and rerun after remediation.

Success measures: independent enforcement evidenced, uncovered routes identified, detection outcomes established, and fixes confirmed without breaking permitted tasks.

Safe and credible by design

Explicit scope approval; synthetic data; test-only destinations; hard request, token, duration, and concurrency caps; operator stop; read-only evidence collection where possible; sensitive-log minimization and controlled retention. Never silently weaken defenses.

Finite scenarios cannot guarantee universal safety, complete RAI coverage, or protection from every cost overrun. Content-safety judgments are not necessarily deterministic. Full kill chain means the defined scenario, not every possible attack. [4]
